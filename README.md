# 舞台监督提示单系统（Stage Cue Manager）

供舞台监督在**排演**与**现场执行**中使用的 Web 应用：录入场次与执行单（灯光 / 音效 / 布景提示及其前置提示），校验后发布不可变执行单；每场演出从某一已发布版本启动独立记录，现场按依赖关系触发或跳过提示，全程留痕。

## 功能

- **场次与执行单管理**：按序编排提示（编号、类型、描述、前置提示）
- **发布前校验**：缺失引用（前置编号不存在）、编号重复、自依赖、循环依赖（给出环路径）
- **不可变执行单**：发布后内容锁定；修改须新建草稿再发布新版本
- **现场执行台**：实时展示 待执行 / 已触发 / 已跳过 / 受阻（前置未触发） 四种状态
  - 仅当前置全部**已触发**时才可触发；受阻项触发按钮禁用且服务端同样拒绝
  - 跳过必须填写原因；每次结果留存操作人与时间
  - 多人并发操作同一提示只记一次有效结果，冲突方会收到当前状态提示
  - **误触发可追溯撤回**：仅当前有效结果为「已触发」的提示可撤回，撤回必须填写撤回人与原因；
    若沿前置关系可达的后续提示仍有效「已触发」则拒绝（422 并列出受影响编号，任何记录不改变）；
    撤回保留原触发与撤回两条流水，提示按当前前置结果重新显示「待执行/受阻」，此后可再次触发或跳过；
    已跳过、未触发（待执行/受阻）的提示不可撤回
- **版本隔离与回看**：演出锁定启动时的已发布版本；排演改草稿不影响进行中的演出，历史演出始终按当时版本回看
- **明确错误**：无已发布版本、非法依赖、前置未满足、缺少操作人 / 原因等均有中文错误提示

## 一键启动（Docker Compose）

```bash
docker compose up --build
```

启动后访问：**http://localhost:3000**

- 首次启动自动初始化数据库（建表），空库时写入一份演示数据（可用 `SEED_DEMO: "0"` 关闭）
- SQLite 数据保存在名为 `cue-data` 的卷中（容器内 `/app/data/app.db`），删除容器不丢数据

## 配置（环境变量）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `PORT` | `3000` | Web 服务端口（compose 中映射为 `宿主机:容器`，改宿主机端口请改 `ports`，如 `"8080:3000"`） |
| `DB_PATH` | `/app/data/app.db`（本地运行为 `./data/app.db`） | SQLite 数据库文件路径 |
| `SEED_DEMO` | `1` | 空库时是否写入演示数据，`0` 关闭 |
| `HOST` | `0.0.0.0` | 监听地址 |

## 本地开发（不用 Docker）

要求 Node.js ≥ 22.13（推荐 24，使用内置 `node:sqlite`，**无任何第三方依赖**）：

```bash
npm start          # 或 node server.js
# 打开 http://localhost:3000
```

## 使用流程

1. **新建场次** → 进入场次后「新建草稿」
2. 在草稿编辑器中按序录入提示，前置提示填编号（逗号分隔）；随时「校验」
3. 「校验并发布」→ 生成不可变执行单（如 v1）
4. 回到场次页「启动演出」，选择已发布版本 → 进入执行台
5. 执行台中填写操作人，对提示执行「触发 / 跳过」，对误触发的已触发提示执行「撤回」（需填撤回人和原因，后续已触发时会被拒绝并列出编号）；页面每 2.5 秒自动刷新，多人可同时操作
6. 排演中要改执行单：新建草稿（自动复制最新版本）→ 修改 → 发布为 v2；新演出即可选 v2，旧演出仍按 v1 回看

## 技术栈与结构

- **后端**：Node.js 内置 `node:http`（API + 静态页面），零第三方依赖
- **数据库**：SQLite（Node 内置 `node:sqlite`），关系型 schema，WAL 模式，事务 + 唯一约束保证并发一致
- **前端**：原生 HTML/CSS/JS 单页应用（hash 路由），无需构建

```
server.js            # HTTP 入口：API 分发、静态文件、统一错误处理
src/db.js            # SQLite 连接、建表初始化、事务包装、演示数据
src/validate.js      # 执行单校验：缺失引用 / 重复编号 / 自依赖 / 循环依赖
src/api.js           # 全部 REST 接口与业务规则
public/              # 前端单页应用（index.html / app.js / style.css）
Dockerfile           # node:24-slim，零依赖构建
docker-compose.yml   # 一键启动 + 数据卷
```

## API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET/POST | `/api/shows` | 场次列表 / 新建场次 |
| GET | `/api/shows/:id` | 场次详情（版本 + 演出记录） |
| POST | `/api/shows/:id/versions` | 新建草稿（默认复制最新版本） |
| GET | `/api/versions/:id` | 版本快照（含提示与前置） |
| PUT | `/api/versions/:id/cues` | 保存草稿（已发布返回 409） |
| POST | `/api/versions/:id/validate` | 校验（缺失引用 / 循环依赖） |
| POST | `/api/versions/:id/publish` | 发布（校验失败 422 并附问题清单） |
| POST | `/api/shows/:id/performances` | 启动演出（无已发布版本返回 400） |
| GET | `/api/performances/:id` | 执行台状态（提示状态 + 事件流水） |
| POST | `/api/performances/:id/cues/:cueId/fire` | 触发（前置未满足 422；已有结果 409 附当前状态） |
| POST | `/api/performances/:id/cues/:cueId/skip` | 跳过（缺原因 400；已有结果 409） |
| POST | `/api/performances/:id/cues/:cueId/recall` | 撤回已触发提示（撤回人 + 原因必填；非已触发 409；后续仍已触发 422 附 `affected` 编号） |

### 撤回接口调用示例

`cueId` 为提示在版本中的自增 id（可由 `GET /api/performances/:id` 返回的 `cues[].id` 取得）。
撤回判定基于该场演出的**当前有效结果**（每条提示最新一条非撤回记录）：

```bash
# 1) 查看执行台：取得各提示 id、当前状态与完整流水
curl -s http://localhost:3000/api/performances/1 | python3 -m json.tool

# 2) 触发提示（误触发场景）
curl -s -X POST http://localhost:3000/api/performances/1/cues/2/fire \
  -H 'Content-Type: application/json' \
  -d '{"operator":"舞台监督甲"}'

# 3) 发现误触，由撤回人填写原因后撤回（成功：原触发与撤回流水均保留）
curl -s -X POST http://localhost:3000/api/performances/1/cues/2/recall \
  -H 'Content-Type: application/json' \
  -d '{"operator":"监督乙","reason":"演员未到位，误触 S1"}'
# 200 -> {"recalled_event":{...原 fired 流水...}, "event":{action:"recalled", reason:..., recalled_event_id:...}}

# 4a) 若后续提示（依赖链可达者）仍有效「已触发」，撤回被拒绝且不改动任何记录
# 422 -> {"error":"撤回被拒绝：后续提示 B1、L2 仍为已触发，请先撤回它们（未改动任何记录）",
#         "affected":["B1","L2"]}

# 4b) 提示为已跳过 / 待执行 / 受阻（无有效「已触发」结果）
# 409 -> {"error":"已跳过的提示不能撤回", "current":{...当前 skipped 结果...}}
# 409 -> {"error":"该提示当前没有有效结果（待执行/受阻），无法撤回"}

# 5) 撤回成功后该提示按前置结果显示 pending/blocked，可再次触发或跳过
```

### 事件流水（events）结构

`GET /api/performances/:id` 的 `events` 按时间倒序返回**完整流水**（含撤回）。
原有字段保持不变，新增两个字段（旧客户端忽略即可）：

| 字段 | 说明 |
| --- | --- |
| `action` | `fired` / `skipped` / `recalled`（新增取值） |
| `effective` | 该条是否为提示的当前有效结果（撤回记录与已被撤回的旧结果均为 `false`） |
| `recalled_event_id` | 撤回记录指向被撤回的原结果事件 id（其它动作为 `null`） |

执行台右侧流水面板展示全部记录：撤回行高亮，已被撤回的旧结果标记「已失效」。

## 数据与并发说明

- `cue_events` 为**追加式流水**：触发 / 跳过写入一条结果，撤回再写入一条 `recalled` 记录（`recalled_event_id` 指向被撤回的结果），任何记录都不删除不修改；提示的「当前有效结果」= 其最新一条非撤回事件
- 触发、跳过、撤回均在 `BEGIN IMMEDIATE` 事务内基于同一有效状态串行判定：同一提示至多一个当前有效结果，并发的失败方收到 409 及当前结果（操作人、时间、原因）；撤回的下游阻塞判定与写入同事务完成，不会出现"检查通过却已不一致"
- 撤回校验沿前置关系做下游可达遍历：任一可达提示当前仍有效「已触发」即整体回滚（422 返回按执行序排列的 `affected` 编号）
- 演出与版本通过外键绑定，版本发布后无更新入口，因此历史回看永远呈现演出当时的执行单内容；撤回流水也只作用于本场演出，其它演出与已发布版本不受影响
- 升级旧版本数据库时自动迁移 `cue_events` 表（解除"每提示唯一"约束、增加撤回动作与 `recalled_event_id` 列），历史触发 / 跳过流水原样保留
